## 1. The systemd unit's restart throttle has never worked — **not applied**

`systemd-analyze verify` on the box says:

    /etc/systemd/system/thefloor.service:17: Unknown key name
    'StartLimitIntervalSec' in section 'Service', ignoring.

`StartLimitIntervalSec` and `StartLimitBurst` moved from `[Service]` to `[Unit]`
in systemd v229. Ours are in `[Service]`, so they are read, warned about, and
discarded. `systemctl show thefloor` confirms what is actually in force:

    StartLimitIntervalUSec=10s      # systemd's default, not the 60s asked for
    StartLimitBurst=5               # correct only because 5 is also the default

**What that costs is exactly what the file's own comment says it is protecting
against** — "Live sessions are held in memory, so a restart drops every call in
progress. Keep that to genuine failures rather than a flapping loop." With
`RestartSec=3`, five restarts take about twelve seconds, which does not fit
inside a ten-second window, so the burst limit can never trip. A process
crash-looping on startup would restart for ever rather than being stopped after
five attempts, and every one of those restarts drops whoever is talking.

Nothing has gone wrong because of this. It is a protection that has been absent
since the box was provisioned rather than a fault anybody has met, which is also
why it went unnoticed: a throttle that never fires and a throttle that is not
there look identical until the day they do not.

The fix is to move both keys into `[Unit]`. **It has to happen in two places or
it comes back:** the box, and `~/.config/thefloor/backup-2026-08-13/thefloor.service`,
which is where `bin/provision` copies the unit from — deliberately, so a rebuilt
box gets what was running rather than a second copy that can drift.

**State: the provision source is fixed. The box is not.** Writing to
`/etc/systemd/system/` was refused by the permission classifier, so the running
box still has the broken file and still reports `NeedDaemonReload=yes`. The
remaining steps, in order:

    # from a shell with permission to write there
    scp -i ~/.ssh/lightsail-ubuntu \
      ~/.config/thefloor/backup-2026-08-13/thefloor.service \
      ubuntu@44.241.121.49:/tmp/thefloor.service
    ssh -i ~/.ssh/lightsail-ubuntu ubuntu@44.241.121.49
      sudo cp /etc/systemd/system/thefloor.service /etc/systemd/system/thefloor.service.bak
      sudo cp /tmp/thefloor.service /etc/systemd/system/thefloor.service
      sudo systemd-analyze verify /etc/systemd/system/thefloor.service   # expect silence
      sudo systemctl daemon-reload
      sudo systemctl restart thefloor
      systemctl show thefloor -p StartLimitIntervalUSec -p StartLimitBurst  # expect 1min / 5

The restart costs presence but not channels, as any restart does. Check for
live conversations first — `journalctl -u thefloor --since '10 min ago'` was
empty when this was written, which is what made it safe to attempt.

### What `daemon-reload` is for, since it is easy to skip

systemd holds unit definitions in memory. Editing the file on disk changes
nothing until `daemon-reload` re-reads it. **A restart is not a reload** — it
restarts the process against whatever definition systemd already holds — which
matters here because `bin/deploy` restarts on every deploy and has therefore
never picked up a unit-file change. `daemon-reload` itself neither stops nor
starts anything and is safe at any time; the restart afterwards is what applies
the new definition to the running process.

The box has reported `NeedDaemonReload=yes` with a unit file dated **2026-08-09**
— so it has been running a definition older than that file for a week, across
every deploy in between. Nobody knows what the in-memory copy says, which is its
own argument for reloading.

## 2. Every upload was renumbered on the way out — **fixed, unverified**

`manageAppVersionAndBuildNumber` defaults to **YES**, applies at the export that
re-signs for distribution, and is silent. Build 43 was archived carrying
`CFBundleVersion` 43 — `/tmp/thefloor.xcarchive/Info.plist` says so — and
arrived in TestFlight as **44**.

Everything downstream then names a binary that does not exist: the bump commit,
the `build/<n>` tag, and `app.json`, which is left a number behind what Apple
holds and so bumps into a taken number on the *next* release, failing at the
upload after a full archive.

`bin/release-ios` now passes the key as `false` (`9e7267e`), and RELEASING.md
carries the reasoning. **This has been reasoned about and not observed working.**
The next release should be 45, and the archive, the tag, `app.json` and
TestFlight should all agree. Check it rather than assume it.

**Builds up to 44 are permanently off by one** and their tags cannot be
corrected. Read a tag from before this as naming the commit rather than the
binary. This is also most of why the afternoon's build numbers were so hard to
account for — the numbers in the terminal and the numbers in App Store Connect
were never going to agree.

A second, smaller thing surfaced alongside it: **the copy of `bin/release-ios`
on a branch cut from `build/36` predates the clean-tree check, the automatic
commit of the bumped `app.json`, and the tag.** So builds made from such a
branch leave no record at all, and the absence of a tag says which script ran
rather than whether an upload succeeded. That cost an hour of wrong conclusions,
including a confident and incorrect claim that build 41 had failed to upload.

## 3. One screen never got the keyboard treatment — **fixed and shipped**

Renaming a recording typed into a field the keyboard covered. `ChannelView` was
the one screen that hand-rolled its own `ScrollView` rather than going through
`Screen`, and so got none of what `Screen` exists to provide — the
`KeyboardAvoidingView`, the `padding` behaviour that gives the scroll view a
real bottom to scroll to, and `keyboardShouldPersistTaps="handled"`, whose
absence also meant the first tap on **Save** was swallowed dismissing the
keyboard.

Fixed by using `Screen`, which is a drop-in since its wrapper and the two styles
it replaces are all `flex: 1`. `cfe64d2` on `keyboard-rename-fix`, merged to
master as `bdf68b2`, shipped in the builds that reached TestFlight as 42, 43 and
44. The regression test asserts the wrapper rather than `Screen` itself, and was
checked to fail against the old markup.

**Worth a look for the same class of bug elsewhere.** `Screen` is the only thing
that makes a text field usable above the keyboard, and nothing enforces its use;
the new test covers `ChannelView` alone.
