# Each episode has a page, a card and clips

Rodrigo, 2026-11-13. Three additions to what `publishable-recordings.md`
built, in this order because each needs the one before it. **Read
`decision/2026-09-21-nothing-is-published-until-everybody-in-it-has-agreed.md`
first**: every part of this touches what was consented to, and the questions
below are mostly that question. The feed is `server/src/feed.ts`, the page
`server/src/public-page.ts`, both fed by `publicChannel()` in `app.ts`.

## 1. A page, an image and a description per episode

Today an *episode* is a line on the channel's public page and an `<item>`
carrying a title, an enclosure, a duration and a transcript. The channel
already has cover art and a description in both. What is asked:

- **A page per episode**, its own URL, linked from the channel page and from
  the item's `<link>`. `/c/:id/e/:file` already answers with the `.m4a`, so
  either that route tells `<rec>.m4a` from a bare `<rec>`, or the page lives
  elsewhere; decide which before the URL is out, since it never changes after.
  Same rules as the channel page: no script, `preload="none"`, nobody named.
- **A description per episode**: the item's `<description>` (plain text, as
  the channel's has been since 2026-09-13, so feed and page cannot disagree)
  and `<itunes:summary>` only if a validator asks. Not generated by default:
  a digest written into a public description is the server making a public
  claim about somebody's conversation. Offering a digest as a draft is fine.
- **An image per episode**: the item's `<itunes:image>`, under the rules
  `artwork.ts` already enforces for the channel's cover (Apple: square,
  1400–3000 px, JPEG or PNG, RGB), stored and cache-busted the same way
  (`image_at` on the URL). With none, the element is omitted and every
  client falls back to the channel's cover. That fallback is correct, not a gap.
- **What else the protocols want on an item**, while it is open:
  `<itunes:title>`, `<itunes:episodeType>full` (which is what makes clips
  below expressible) and `<itunes:episode>` only if numbering means anything
  here. Check against a feed validator and Apple's current spec; `ts health`
  is not the check.

**Open, and the user's to answer:** who may set an episode's title,
description and image, and whether changing one after everybody agreed to
publish reopens consent. The title already has a privacy guard
(`publicTitle`); a description is free text and could name a member, which the
channel's description may do only because its members wrote it.

## 2. A social card for the channel and each episode

The public pages carry `socialCard()`'s tags (`html.ts`), but the image is the
site's own `og.png`, so a pasted podcast link previews as The Floor rather
than as the podcast. Asked: a card for `/c/<id>` and for each episode page.

- `og:title`, `og:description`, `og:url` (these URLs carry no secret, so the
  canonical path is right), `og:type`, and `og:image` as the episode's art,
  else the channel's cover, else `og.png`, versioned by `image_at`.
- `og:audio` pointing at the `.m4a`, with its type. Cheap, and some
  clients use it.
- `twitter:card` as `summary` because the art is square. `player` would play
  inline on X, but it needs an iframe player page and X's approval, and it is
  a script on a page that has none.
- **A composed 1200×630 image** (cover beside title) previews better than a
  square one letterboxed. There is no image library on the server; ffmpeg
  is on the box and can draw text over an image. It is a refinement, so
  ship the cover first.
- Preview fetches will show in `ts usage` with the rest of the public page.
  Check they are not counted as *episode starts*.

## 3. Clips

A clip is a stretch of a published episode, from a start time to an end. The
ask is a separate podcast feed of them, or a better recommendation. The
options, cheapest first:

1. **`<podcast:soundbite startTime duration>`** on the episode's item.
   Standard (Podcasting 2.0), no new audio, no new feed. Fountain, Podverse
   and Castamatic surface it; Apple and Spotify ignore it.
2. **A clip page**: `/c/<id>/e/<rec>?t=754-812`, or a short id, with its own
   card (part 2) and the episode's audio played from that range by a media
   fragment (`#t=754,812`). This is what most people mean by a clip: a link
   to share. It needs no new bytes and dies with its episode by construction.
3. **An adjacent feed**, `/c/<id>/clips.xml`, a second podcast whose items are
   cut files (ffmpeg, re-encoded to AAC like an episode), each linking back to
   its episode page. Subscribable as a highlights show, but it is a second
   show to submit to directories with its own art, and its stored bytes
   need the sweep to know about them.
4. **Clips in the same feed as `<itunes:episodeType>bonus`**. Rejected:
   subscribers get the same voices twice and the episode list fills with
   fragments.

**Recommended: 1 and 2 together first, then 3 if somebody asks to subscribe
to highlights.** One table of clips (recording, start, end, title) feeds all
three, so starting small leaves nothing to undo. Whichever is built:

- **A clip goes when its episode goes.** It leaves the moment the episode is
  unpublished or marked deleted, before its bytes go, which is the ordering
  `publicChannel()` already argues for episodes.
- **Whether a clip needs its own consent is open.** It is a subset of
  something everybody agreed to, but a minute out of context is not what
  they agreed to. Unanimity again is the safe reading. Whoever settles it
  writes the decision.
- Clip boundaries want word-level timestamps, which batch transcripts have.
  `a-playlist-of-the-best-lines-in-their-own-voices.md` asks for the same
  extraction from the inside, so the two should share the table.
- *Clip* is a new word, and goes in the glossary when it ships, beside
  *Episode*, with *Episode page*.
